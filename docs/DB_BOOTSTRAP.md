# Развёртывание базы данных: как это работает с 30.07.2026

## Проблема, которую чинили

Базовые таблицы (`users`, `counterparties`, `contracts`, ...) исторически создаёт
TypeORM `synchronize` из моделей, а миграции их только изменяют. При этом
`migrationsRun: true` в DataSource выполнял миграции **до** synchronize, поэтому
на пустой базе первая же миграция склада падала на отсутствующей
`counterparties` — развернуть проект с нуля было невозможно. Дополнительно
`database/init/01-init.sql` (монтировался в docker initdb) создавал `users`
устаревшей формы: без `timezone`/`workday_*` и без роли `hr_recruiter` в CHECK.

## Как стало

Порядком управляет `backend/src/services/db-bootstrap.service.ts`
(`ensureDatabaseSchema()`, вызывается при старте до `ensureDefaultAdmin`):

1. **Пустая база** (нет таблицы `users`) → строится полная текущая схема из
   моделей (`synchronize()`), затем все входящие в сборку миграции помечаются
   применёнными в `typeorm_migrations` — их изменения уже включены в модели.
2. **Живая база** → схема не трогается; при `DB_MIGRATIONS_RUN=true`
   выполняются только новые (pending) миграции.
3. **Отставшая база** (есть `users`, нет `counterparties` — состояние
   «только 01-init.sql») → в лог пишется предупреждение с указанием применить
   `database/patches/*.sql` либо начать с пустой базы. Автоматически такая база
   не чинится: synchronize на ней разрушителен (drop/alter legacy-таблиц).

В `config/data-source.ts` `migrationsRun` теперь выключен намертво; флаг
`DB_MIGRATIONS_RUN` обрабатывается в bootstrap-сервисе. Из
`backend/docker-compose.yml` убрано монтирование `database/init` — новый том
Postgres начинается пустым, дальше всё делает приложение.

## Что это означает на практике

- **Разработчик с нуля**: `docker-compose up -d` → `npm start` → готово.
  Админ создаётся из `DEFAULT_ADMIN_EMAIL`/`DEFAULT_ADMIN_PASSWORD`.
- **Слияние с main** (склад, договоры, проверки кандидатов развиваются там):
  их новые миграции после merge выполняются как pending на живых базах при
  `DB_MIGRATIONS_RUN=true`; на свежих базах не нужны вовсе — схема берётся из
  моделей. Правило для авторов миграций остаётся прежним: писать идемпотентно
  (`IF NOT EXISTS`), как это уже сделано в большинстве существующих.
- **Существующие отставшие базы** приводятся точечными патчами из
  `database/patches/` (созданы 30.07.2026: `2026-07-30-hh-module-full.sql`,
  `2026-07-30-users-catchup.sql`). Оба идемпотентны.

## Проверено (30.07.2026, PostgreSQL 16)

- Пустая база → старт: 59 таблиц, 21 миграция проштампована, отвечают все
  модули: склад, договоры, проверки кандидатов, планирование, HR (200),
  админ создаётся и входит.
- Перезапуск на той же базе: «новых миграций нет», без изменений.
- Имитация «догнала миграция из main» (удалены таблицы заявок и штамп):
  при `DB_MIGRATIONS_RUN=true` выполнилась ровно она, таблицы восстановлены.
- Отставшая база 01-init: предупреждение в лог, сервер работает на патчах.

## Ограничения

- `DB_SYNCHRONIZE=true` на живой базе по-прежнему опасен (перестройка схемы с
  DROP) — не включать; флаг оставлен только для совместимости.
- Изменены общие файлы: `backend/src/index.ts`, `backend/src/config/data-source.ts`,
  `backend/docker-compose.yml` — при merge с main диффы маленькие, но про них
  нужно помнить.

## Правила для авторов миграций

Схема в этом проекте живёт в двух местах: **модели** (из них строится пустая
база) и **миграции** (ими изменения доставляются на живые базы). Поэтому почти
каждое изменение существует в двух экземплярах, и любая база может встретить
миграцию с уже применённым изменением — после synchronize у разработчика,
после catch-up патча, после восстановления бэкапа. Отсюда главное правило:

> **Миграция обязана молча пережить случай «это изменение здесь уже есть».**
> Повторный запуск = тот же результат, без ошибки.

### Паттерны по типам операций

| Операция | Как писать |
|---|---|
| Новая таблица | `CREATE TABLE IF NOT EXISTS` |
| Новая колонка | `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` |
| Индекс | `CREATE [UNIQUE] INDEX IF NOT EXISTS` |
| Enum-тип | `IF NOT EXISTS` не существует → `DO $$ ... IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = '...') THEN CREATE TYPE ...` (образец: `1783140000000-AddContractIncomeKind.ts`) |
| Constraint | `IF NOT EXISTS` не существует → паттерн «rebuild»: `DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT` (образец: `1783130000000-AddHrRecruiterRole.ts`) |
| Данные | `UPDATE ... WHERE <ещё не заполнено>`; `INSERT ... ON CONFLICT DO NOTHING` или `WHERE NOT EXISTS` |
| NOT NULL колонка на живой таблице | три шага: ADD nullable/с DEFAULT → backfill → `SET NOT NULL`; каждый шаг защищён |
| Чужая таблица (другой модуль) | проверить `to_regclass('public.имя')` и упасть с понятным сообщением, а не с «relation does not exist» |
| `down()` | всё с `IF EXISTS` |

### Чек-лист перед коммитом миграции

1. Изменение внесено **и в модель, и в миграцию** (иначе пустые базы и живые
   базы разъедутся).
2. Миграция прогнана **дважды подряд** на dev-базе — второй запуск no-op.
3. `down()` прогнан и тоже идемпотентен.
4. Нет ссылок на таблицы, которых может не быть, без проверки существования.
5. Имя класса заканчивается timestamp'ом (`...1785400000000`) — по нему
   bootstrap вычисляет порядок и штампует baseline.

Аудит 30.07.2026: все 21 существующие миграции соответствуют правилам.
Единственная неидемпотентная (`1782192000000-AddWarehouseContractEndDate`)
исправлена — добавлены `IF NOT EXISTS`/`IF EXISTS`, поведение не изменилось.
