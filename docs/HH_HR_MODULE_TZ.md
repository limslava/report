## 1. Цель и контекст

Сейчас подбор персонала ведётся полностью в веб-кабинете hh.ru: рекрутер создаёт вакансии, разбирает отклики, ведёт кандидатов по этапам в интерфейсе hh, а внутренняя отчётность по найму (сколько закрыто, за какой срок, откуда пришли кандидаты, нагрузка на рекрутеров) собирается вручную. Данные о найме не связаны с остальным контуром Report — планированием, графиками работы, БП и дашбордами руководства.

Цель модуля — встроить работу рекрутинга в Report **полным циклом**:

1. публикация и ведение вакансий hh из Report (создание, редактирование, продление, архивация, скрытие, черновики);
2. приём откликов и приглашений в реальном времени (webhooks) с ведением **собственной воронки подбора** внутри Report и синхронизацией статусов обратно в hh;
3. карточка кандидата с резюме, историей этапов, комментариями, интервью и вложениями;
4. отчётность по найму (воронка, срок закрытия вакансии, источники, нагрузка рекрутеров, стоимость публикаций) в едином корпоративном виде системы.

Модуль строится как **отдельный изолированный модуль** — по образцу модулей «Склад ТС» и «Проверка кандидатов»: собственный префикс таблиц (`hh_`), собственные маршруты (`/api/hh/*`, UI `/hr/*`), собственные права. Общими остаются пользователи, роли, авторизация JWT, SMTP, WebSocket, планировщик и аудит.

**Ключевое архитектурное решение:** источником истины по кандидату остаётся hh (там персональные данные), источником истины по внутреннему процессу подбора — Report. Report хранит идентификаторы и собственную воронку, а персональные данные тянет из hh по запросу и хранит в минимальном объёме с ограниченным сроком (см. раздел 8.2).

## 2. Результаты обследования внешней системы (28.07.2026)

### 2.1. Общее устройство

- Базовый URL — `https://api.hh.ru`, единый для всех площадок; площадка выбирается query-параметром `host` (`hh.ru`, `hh.kz`, `rabota.by`, `hh.uz`, `hh1.az`, `headhunter.ge`, `headhunter.kg`), по умолчанию `hh.ru`. Локаль — `locale` (по умолчанию `RU`).
- Формат — REST/JSON, даты ISO 8601 `YYYY-MM-DDThh:mm:ss±hhmm`.
- Документация переведена в OpenAPI 3.0.3: ReDoc — `https://api.hh.ru/openapi/redoc`, Swagger — `https://api.hh.ru/openapi/swagger`, **сырая спецификация — `https://api.hh.ru/openapi/specification/public`**. Спецификацию нужно скачать в начале работ и зафиксировать в репозитории (см. п. 6.1) — часть старых markdown-документов из `github.com/hhru/api` удалена при миграции на ReDoc.
- Ошибки: `{"errors":[{"type":"...","value":"..."}],"request_id":"..."}`. `request_id` обязателен при обращении в поддержку `api@hh.ru`. При 5xx тело может не быть валидным JSON — ориентироваться только на код.
- Пагинация: `page` (с 0) + `per_page`; корневой объект `{found, per_page, pages, page, items}`.
- Кэширование: справочники отдают `ETag` / `Cache-Control`; поддерживается `If-None-Match` → `304`. HEAD работает.

### 2.2. Обязательный заголовок User-Agent

Дословно из документации:

> «В запросе необходимо передавать заголовок `User-Agent`, но если ваша реализация http клиента не позволяет, можно отправить `HH-User-Agent`. **Если не отправлен ни один заголовок, то ответом будет `400 Bad Request`.** … в случае, если вы отправите оба заголовка, обработан будет только `HH-User-Agent`.»

Формат: `User-Agent: ReportHR/1.0 (it@<домен-компании>)`. Ошибки: `400 bad_user_agent / unset`, `400 bad_user_agent / blacklisted`.

**Требование к реализации:** заголовок задаётся централизованно в HTTP-клиенте модуля (`hh-client.service`), значение — из переменной окружения `HH_USER_AGENT`. Ни один запрос к hh не должен уходить в обход этого клиента.

### 2.3. Авторизация (OAuth 2.0)

| Шаг | Запрос |
|---|---|
| Форма согласия | `GET https://hh.ru/oauth/authorize?response_type=code&client_id=...&redirect_uri=...&state=...` |
| Обмен кода на токен | `POST https://api.hh.ru/token` (старый `https://hh.ru/oauth/token` — устарел) |
| Обновление | `POST https://api.hh.ru/token`, `grant_type=refresh_token`, `refresh_token=...` (client_id/secret **не нужны**) |
| Токен приложения | `POST https://api.hh.ru/token`, `grant_type=client_credentials` |
| Отзыв | `DELETE https://api.hh.ru/token` → 204 (пути `/oauth/token` для отзыва не существует) |

Тело — `application/x-www-form-urlencoded`. Ответ: `{"access_token","token_type":"bearer","expires_in":1209600,"refresh_token"}` — **14 суток** для пользовательского токена (ориентироваться на поле, а не на константу).

Критичные правила, которые определяют дизайн хранения токенов:

> «`refresh_token` можно использовать только один раз и только по истечению срока действия `access_token`.»

- Попытка обновить ещё живой токен → `invalid_grant / token not expired`.
- Повторное использование refresh → `invalid_grant / token has already been refreshed`, **старая пара при этом уже мертва** → требуется повторная авторизация пользователя.
- Прочие: `token was revoked`, `token deactivated` (пользователь сменил пароль на hh), `bad token`.

**Требование:** обновление токена выполняется строго под распределённой блокировкой (Redis-lock либо `SELECT ... FOR UPDATE` по строке подключения), новая пара сохраняется атомарно в одной транзакции. Гонка двух воркеров = потеря доступа и ручная переавторизация.

Токен приложения (`client_credentials`) — бессрочный, но: запрашивать не чаще 1 раза в 5 минут (`403 forbidden / app token refresh too early`), при повторном запросе старый отзывается. **Для работодательских методов он не годится** — вернёт `403 oauth / user_auth_expected`. В модуле используется только пользовательский токен менеджера работодателя.

`redirect_uri`: разрешено уточнение поддомена, пути и добавление query-параметров относительно сохранённого в настройках; запрещена смена протокола, домена, «соседний» путь и добавление порта.

Проверка токена и получение контекста — `GET /me`:
- `auth_type` ∈ `applicant | employer | application | employer_integration`;
- `employer.id` → **это `employer_id`**;
- `manager.id` → **`manager_id`** (поле `employer.manager_id` объявлено устаревшим);
- флаги `manager.has_admin_rights`, `manager.is_main_contact_person`, `manager.has_multiple_manager_accounts`.

Мультиаккаунт: если `has_multiple_manager_accounts = true` → `GET /manager_accounts/mine`, далее во всех работодательских запросах передавать заголовок `X-Manager-Account-Id: {account_id}`. Ошибки: `403 manager_extra_accounts / manager_extra_account_not_found`, `403 manager_accounts / used_manager_account_forbidden`.

Замечания, которые часто ломают интеграции:
- архивация — это **НЕ** `/vacancies/{id}/archive`, а `PUT /employers/{employer_id}/vacancies/archived/{vacancy_id}`;
- продление — `POST /vacancies/{vacancy_id}/prolongate`, не через `/employers/...`;
- **восстановления из архива нет** — нужно публиковать заново через `POST /vacancies` с `previous_id` = ID архивной вакансии (все остальные поля передавать заново);
- `PUT /vacancies/{id}` (`VacancyEdit`) — это `anyOf` из **четырёх** вариантов запроса: `VacancyEditCommon` (без обязательных полей — обычное редактирование), `VacancyEditBillingType` (`required: [billing_type]`), `VacancyEditVacancyProperties` (`required: [vacancy_properties]`), `VacancyEditManager` (`required: [manager]`). То есть `billing_type`, `vacancy_properties` и `manager` меняются **каждый своим отдельным запросом**, а не вместе и не в общем теле. Документация прямо предупреждает: *«Составные поля (например, `salary_range`, `contacts`, `professional_roles`) можно редактировать только целиком… Поля `billing_type` и `manager` необходимо передавать в отдельном запросе»*;
- все вакансии проходят **ручную модерацию** hh; при успешной публикации списываются услуги;
- стоимость продления равна стоимости новой публикации; возможность и причина отказа определяются вызовом `GET /vacancies/{id}/prolongate` (справочник `vacancy_not_prolonged_reason`, 9 значений — `vacancy_archived`, `not_enough_quotas`, `not_enough_purchased_services` и др., временны́х ограничений среди них нет). Встречающееся в старой документации правило «не чаще раза в минуту» в актуальной спецификации не подтверждается — полагаться на предварительный вызов, а не на таймер.

**Обязательные поля при создании вакансии.** `VacancyCreate` — это `anyOf` из двух взаимоисключающих наборов:

| Вариант | `required` |
|---|---|
| `VacancyCreateFieldsWithProperties` — **актуальный** | `name, description, area, professional_roles, vacancy_properties` |
| `VacancyCreateFields` — legacy («используя устаревшие поля `billing_type` и `type`») | `name, description, area, professional_roles, type, billing_type` |

Все семь полей одновременно обязательными не бывают. `billing_type` в спецификации помечен «*Заменён на параметр `vacancy_properties`*», `type` — «*значения open/close заменены на `closed_for_applicants`, а anonymous/direct — на `vacancy_properties` (HH_ANONYMOUS, HH_ADVERTISING)*».

**Требование:** модуль реализует **актуальный вариант** с `vacancy_properties` и `closed_for_applicants`; legacy-поля `type` / `billing_type` не используются при создании и хранятся только для чтения ранее созданных вакансий.

Модель воронки на стороне hh (дословно):

> *коллекция* — «набор откликов/приглашений, объединённых по определённым критериям… **Не стоит полагаться на то, что в определённые этапы обработки отклика/приглашения оно будет входить в известные коллекции, так как эта логика может изменяться.**»
> *работодательское состояние* (`employer_state`) — «**зависит от вакансии и работодателя**, поэтому список необходимо запрашивать, передавая нужную вакансию».
> *действие* (`actions[]`) — берётся из ответа: `actions[].url` + `actions[].arguments` + `resulting_employer_state`.

**Важно про два разных набора значений.** Поле `employer_states` в ответе `GET /negotiations` — это фильтр списка, и его базовые значения: `response`, `invitation`, `discard`, `discard_after_interview`. Но целевые состояния переходов приходят в `actions[].resulting_employer_state.id` и образуют **другой, более широкий набор**: `response`, `consider`, `phone_interview`, `interview`, `assessment`, `offer`, `hired`, `invitation`, `discard_by_employer`. При этом `discard_after_interview` — это идентификатор **шаблона письма** (`/message_templates/discard_after_interview?topic_id=...`), а не состояние; состояние отказа называется `discard_by_employer`.

**Требование:** маппинг внутренних этапов Report ведётся на значения `resulting_employer_state`, а не на значения фильтра `employer_states`. Переходы выполняются **исключительно** через `actions[].url` + `arguments` из свежего ответа API. Захардкоженные URL действий и жёсткая привязка к именам коллекций запрещены — hh явно оставляет за собой право менять эту логику.

Смена соискательского статуса происходит только если отправлено сообщение — в теле действия (`message`) либо отдельным вызовом.

Отклик считается просмотренным при одном из: запрос `messages` по URL из коллекции, `GET /negotiations/{nid}/messages`, запрос резюме по URL из коллекции, `POST /negotiations/read`.

**Переписка: старое API устарело, новое — есть.** Методы `GET/POST /negotiations/{nid}/messages` помечены в спецификации: *«‼️ Методы устарели, и более не поддерживаются, необходимо использовать новые методы для работы с чатами»*; для работодателя `POST` возвращает `Content-Type: text/html`. Актуальный раздел — **«Чаты», ~15 операций, без пометки deprecated**:

`GET/POST /common/chats/{chat_id}/messages` · `PUT/DELETE /common/chats/{chat_id}/messages/{message_id}` · `PUT /common/chats/{chat_id}/message/{message_id}/read` · `GET /common/chats` · `GET /common/chats/counters/unread` · `GET/PUT /common/chats/{chat_id}/participants` · `PUT /common/chats/{chat_id}/write_possibility` · `PUT /common/chats/{chat_id}/leave` · `POST /common/chats/without_vacancy` · `POST /common/chats/files/upload_links` · `GET /common/chats/files/conditions`.

`chat_id` приходит в payload вебхуков `NEW_NEGOTIATION_VACANCY` и `NEW_RESPONSE_OR_INVITATION_VACANCY`.

**Решение по объёму:** отказ от чата — это решение по объёму работ, а не отсутствие API. В v1 реализуется **чтение переписки и отправка текстовых сообщений через `/common/chats/*`** плюс сопроводительный текст внутри действий (приглашение / отказ / шаблон). Вложения (`/common/chats/files/*`), групповые участники и чаты вне вакансии — вынесены на этап 5. Устаревшие `/negotiations/{nid}/messages` не используются нигде.

| GET | `/resumes/{resume_id}/negotiations_history` | история откликов кандидата (≤30 вакансий) |
| GET/POST/PUT/DELETE | `/applicant_comments/{applicant_id}` | комментарии к кандидату на стороне hh — **платно** |

Скачивание резюме в PDF/RTF отдельного пути не имеет: ссылка приходит **внутри объекта резюме** в полях `download` / `download_with_contact` вида `https://api.hh.ru/resumes/{id}/download/{Имя}.pdf?type=pdf`, при необходимости с `&with_contact={hash}` и `&topic_id=...&vacancy_id=...`. Запрашивать с теми же обязательными заголовками.

Поконтактная модель (критично для бюджета):

> «Работодатели, использующие новый тариф, должны явно открывать контактную информацию… в API приходят специальные ссылки в поле `actions`. При использовании этих ссылок будет списание контакта у клиента. Также при приглашении соискателя на вакансию будет происходить списание контакта. Списание происходит только один раз… **Если соискатель откликнулся первым, списание происходить не будет.**»
> «при запросе контактов возможна ситуация, когда пользователь скрыл контактные данные, тогда просмотр спишется, а в теле ответа придут null… необходимо смотреть на наличие интересующих вас полей в `hidden_fields`»

К контактным относятся: `last_name/first_name/middle_name`, `contact` с `type=cell`, `contact` с `type=email`, `site`, `photo`. Значения `hidden_fields`: `names_and_photo`, `phones`, `email`, `other_contacts`, `experience`. При недоступности полного просмотра часть полей `null`, флаг `can_view_full_info: false`.

**Требование:** открытие контактов — только явное действие пользователя с подтверждением («Открыть контакты — будет списан 1 контакт»), с проверкой `hidden_fields` до вызова и записью факта списания в аудит. Автоматическое открытие контактов при синхронизации запрещено.

**Справочники**

`GET /dictionaries` (`vacancy_billing_type`, `vacancy_type`, `employment`, `experience`, `schedule`, `negotiations_state`, `resume_hidden_fields`, `currency`, `education_level`, `language_level`, `driver_license_types` и др.), `/areas`, `/areas/countries`, `/metro`, `/professional_roles`, `/industries`, `/languages`, `/skills`, `/suggests/*`.

**`/specializations` в актуальной спецификации отсутствует** — заменён на `/professional_roles`.

Предупреждение hh: *«Значения в справочниках могут поменяться в любой момент. Не нужно завязываться на них.»* → справочники кэшируются с `ETag`, но не хардкодятся в коде; идентификаторы хранятся строками.

### 2.5. Webhooks

| Метод | Путь |
|---|---|
| GET | `/webhook/subscriptions` |
| POST | `/webhook/subscriptions` → 201 |
| PUT | `/webhook/subscriptions/{subscription_id}` → 204 |
| DELETE | `/webhook/subscriptions/{subscription_id}` → 204 |

Тело подписки: `{"url":"https://...","actions":[{"type":"...","settings":{"vacancies_only_mine":false}}]}`. **`settings` есть не у всех типов** — у `VACANCY_PUBLICATION_FOR_VACANCY_MANAGER`, `CHAT_CREATED` и `CHAT_MESSAGE_CREATED` этого свойства нет вообще, отправлять его туда нельзя.

Типы событий — **девять** (`discriminator.mapping`), модуль использует все:

| `type` | Payload (обязательные поля) | Использование |
|---|---|---|
| `NEW_NEGOTIATION_VACANCY` | `topic_id, chat_id, resume_id, vacancy_id, employer_id, negotiation_date` | новый отклик → создание записи в воронке |
| `NEW_RESPONSE_OR_INVITATION_VACANCY` | `topic_id, chat_id, resume_id, vacancy_id, employer_id, response_date` | отклик или приглашение |
| `NEGOTIATION_EMPLOYER_STATE_CHANGE` | `topic_id, vacancy_id, from_state, to_state, employer_manager_id, resume_id, transferred_at` | обратная синхронизация этапа |
| `VACANCY_CHANGE` | `vacancy_id, change_date` | точечное обновление вакансии |
| `VACANCY_ARCHIVATION` | `vacancy_id, archivation_date` | снятие вакансии с внутренних витрин |
| `VACANCY_PROLONGATION` | `vacancy_id, prolongation_date` | обновление срока |
| `VACANCY_PUBLICATION_FOR_VACANCY_MANAGER` | `vacancy_id, previous_vacancy_id, employer_manager_id, creation_date` | публикация; `previous_vacancy_id` связывает переопубликованную вакансию с архивной — нужен сценарию 4.5.6 |
| `CHAT_CREATED` | `chat_id, creation_time, type` | создание чата |
| `CHAT_MESSAGE_CREATED` | `chat_id, message_id, message_type, sender_participant_id, is_current_participant, creation_time, role` | новое сообщение в чате |

Доставка — `POST` JSON: `{"id","subscription_id","action_type","user_id","payload":{...}}`. Поле `user_id` помечено `deprecated` («*может быть равно 0 для обратной совместимости*») — не использовать как ключ.

Правила доставки (дословно):

> «В рамках одного приложения пользователь может получать уведомления только на 1 url»
> «ожидается ответ с кодом `2хх Success`… или `409 Conflict`, если пришел дубликат. Для определения дубликатов нужно использовать `id` из запроса»
> Дубликаты возможны, если «url … не ответил в течение **5 секунд**; сервер не смог установить соединение с url…; url ответил неожиданным кодом (отличным от `2xx Success` или `409 Conflict`)»
> «Если в рамках одной подписки ожидаемые ответы не поступают долгое время… **подписка попадает в очередь на блокировку**, а отправки прекращаются.»
> «**Вебхуки не являются средствами гарантированной доставки.**»
> «При удалении приложения владельцем или отзыве пользователем доступа у приложения **все подписки на уведомления удаляются**. После восстановления доступа необходимо оформить новую подписку.»

Последнее правило напрямую связано со сценарием `needs_reauth` (4.1) и задачей `hh:token-health` (4.4): после повторной авторизации подписки нужно создавать заново, а не считать существующими.

**⚠️ Подписи запроса (HMAC) в спецификации нет** — строки `HMAC`, `signature`, `X-HH-*` отсутствуют полностью. Из объявленных в OpenAPI header-параметров есть только `HH-User-Agent` (`X-Manager-Account-Id` описан прозой в `GET /manager_accounts/mine` и применим ко всем работодательским методам).

**Требования к приёмнику вебхуков:**
1. секретный сегмент в URL подписки (`/api/hh/webhooks/{secret}`), секрет длиной ≥ 32 символа, хранится в БД подключения;
2. приёмник **не выполняет бизнес-логику синхронно** — только валидация, запись в `hh_webhook_events` и `200` в пределах бюджета hh (таймаут hh — **5 секунд**; внутренний целевой бюджет модуля — 1 секунда); обработка — фоновым воркером;
3. идемпотентность по `id` события (уникальный индекс); повтор → `409 Conflict`;
4. вебхуки **дублируют**, а не заменяют периодическую синхронизацию (см. п. 4.4) — гарантии доставки нет;
5. мониторинг: доля 409 и время ответа приёмника выводятся в `/health` модуля.

### 2.6. Лимиты и платные методы

Числовых глобальных rate limits hh **не публикует**. Документированы точечные ограничения:

- `429 resumes / view_limit_exceeded` — суточный лимит просмотров резюме; текущий — `GET .../managers/{manager_id}/limits/resume`;
- `403 resumes / quota_exceeded` — квота просмотров менеджера;
- пакет `API_LIMITED` с `balance.actual` — лимит запросов к просмотру резюме из поиска;
- `429` на `POST /vacancies/drafts` — превышено число черновиков;
- `403 vacancies / quota_exceeded`, `403 vacancies / not_enough_purchased_services` — квоты публикаций;
- ≤ 50 `topic_id` за запрос в `POST /negotiations/read` и `PUT /negotiations/{id}`;
- капча: `captcha_required` с `captcha_url` / `fallback_url` (при запросах без токена);
- глубина выдачи: вакансии — 2000, резюме — 2000, работодатели — 5000.

Практически hh применяет недокументированный троттлинг по IP/токену/приложению, реакция — 403/429/капча.

**Требование:** весь исходящий трафик к hh идёт через очередь с ограничителем скорости (стартовое значение — не более 5 запросов/сек и не более 1 параллельного запроса на «тяжёлые» методы резюме), с экспоненциальным бэкоффом и джиттером на 429/503, и с раздельными очередями для фоновой синхронизации и действий пользователя (действия пользователя имеют приоритет).

Платного доступа (бейдж «employer with paid access») требуют: просмотр резюме, **вся работа с откликами**, переписка, поиск по базе резюме и сохранённые поиски, шаблоны сообщений, история откликов кандидата, комментарии к кандидату, инструменты оценки. Проверка — `.../managers/{manager_id}/method_access`; при отсутствии — `403 api_access_payment / action_must_be_payed`. Покупка — только через персонального менеджера hh.

> «при работе приложения от имени нескольких учетных записей работодателей (`employer_id`), у каждой учетной записи работодателя должен быть доступ к платным методам API»

### 2.7. Порядок подключения работодателя

1. Регистрация приложения на `https://dev.hh.ru/admin` → `client_id`, `client_secret`, `redirect_uri`. **Модерация — до 15 рабочих дней** (цитата FAQ hh); повлиять на срок нельзя.
2. Компания покупает у персонального менеджера hh услугу доступа к платным методам API (`API_UNLIMITED` или `API_LIMITED`) — **на каждый `employer_id`**.
3. Авторизуется **менеджер работодателя** через `authorization_code`. Токен приложения для работодательских методов не подходит.
4. `GET /me` → `employer.id`, `manager.id`, флаги прав.
5. При `has_multiple_manager_accounts` → `GET /manager_accounts/mine` + заголовок `X-Manager-Account-Id`.
6. Проверка `method_access` и `services/payable_api_actions/active`.
7. Проверка `vacancies/available_types` — может ли менеджер публиковать.
8. `POST /webhook/subscriptions`.

Права менеджера: публикация требует `can_create_vacancy`, контакты — `can_view_resume_contacts`. Подключать следует менеджера с админ-правами (`has_admin_rights`), иначе `/managers`, `/addresses` и корпоративные справочники вернут 403/404.

## 3. Границы модуля

**Входит в v1:**
- подключение и обслуживание OAuth-сессии работодателя;
- зеркало и управление вакансиями (черновик → публикация → продление → архив);
- приём откликов (webhooks + добор синхронизацией), собственная воронка подбора, синхронизация статусов в hh;
- карточка кандидата, резюме (просмотр и PDF по запросу), контролируемое открытие контактов;
- интервью (планирование, участники, результат) — внутри Report;
- переписка с кандидатом через актуальное API чатов (`/common/chats/*`): чтение, отметка прочитанным, отправка текста;
- уведомления (email + WebSocket-бейджи);
- отчётность по найму;
- роли и права, аудит, health.

**Не входит в v1:**
- вложения в чате, групповые участники и чаты вне вакансии (`/common/chats/files/*`, `participants`, `without_vacancy`) — само API доступно, это ограничение объёма, а не возможностей;
- поиск по базе резюме и сохранённые поиски (`GET /resumes`, `/saved_searches/*`) — отдельная платная услуга, этап 5;
- оформление приёма на работу, кадровый учёт, трудовые договоры;
- интеграция с БП «Проверка кандидатов» — по решению заказчика вынесена за границы v1 (см. раздел 11);
- другие job-борды (Avito Работа, SuperJob) — архитектура клиента делается провайдер-нейтральной, но реализуется только hh;
- загрузка логотипа компании (в API hh отсутствует).

## 4. Функциональные требования

### 4.1. Настройки подключения (роль: `admin`)

Новая вкладка **«Интеграция hh.ru»** на существующей странице `/settings` (рядом с «Уведомления», «Почта», «НДС»).

Содержание вкладки:
- `client_id`, `client_secret` (secret — write-only, в GET возвращается маска), `redirect_uri`, `HH_USER_AGENT`;
- кнопка **«Подключить аккаунт hh»** → редирект на `https://hh.ru/oauth/authorize` с `state` (anti-CSRF, TTL 10 минут, хранится в Redis/БД);
- после возврата — карточка подключения: компания (`employer.name`), менеджер (`manager.full_name`), `employer_id`, `manager_id`, `auth_type`, дата истечения `access_token`, выбранный `X-Manager-Account-Id`;
- блок **«Доступ и услуги»**: результат `method_access` (4 группы), активные услуги `payable_api_actions/active` с остатком пакета `API_LIMITED`, суточный лимит просмотров резюме, доступные типы публикаций;
- блок **«Вебхуки»**: список подписок, кнопка «Пересоздать подписки», URL приёмника (секрет — маска + кнопка «Показать»/«Перевыпустить»), счётчики принятых/дублей/ошибок за 24 ч;
- блок **«Синхронизация»**: последний запуск, длительность, количество объектов, ошибки, кнопка «Синхронизировать сейчас»;
- кнопка **«Отключить»** → `DELETE /token` + удаление подписок + перевод подключения в статус `disconnected` (данные модуля сохраняются). Учесть: при отзыве доступа пользователем hh удаляет подписки на вебхуки сам — после повторного подключения их нужно создавать заново.

Требования:
- `client_secret` и токены хранятся в БД **в зашифрованном виде** (AES-256-GCM, ключ из `HH_CRYPTO_KEY`), в логи и в API-ответы не попадают;
- при истечении refresh или ошибке `token was revoked` — статус подключения `needs_reauth`, письмо администратору и `head_hr`, баннер в UI кабинета;
- поддержка нескольких подключений (`employer_id`) заложена в схему данных, но в v1 в UI активно одно.

### 4.2. Клиент внешнего API (`hh-client.service`)

- единая точка исходящих запросов; `User-Agent`/`HH-User-Agent`, `Authorization: Bearer`, `X-Manager-Account-Id` подставляются автоматически;
- прозрачное обновление `access_token` под блокировкой при `401 token_expired` (не заранее, не «по таймеру» — иначе `token not expired`);
- очередь и rate-limit (п. 2.6), таймауты (connect 5 с, read 20 с, для скачивания PDF — 60 с), ретраи на 429/500/502/503/504 с экспоненциальным бэкоффом и джиттером, максимум 5 попыток;
- обработка `captcha_required`: запрос не ретраится, подключение помечается `captcha_required`, уведомление администратору;
- маппинг ошибок hh → внутренние: `api_access_payment` → 402 «Требуется платный доступ к API hh», `quota_exceeded` → 409, `view_limit_exceeded` → 429 с текстом о суточном лимите;
- логирование каждого запроса: метод, путь (без query с ПДн), код, длительность, `request_id` из ответа hh — в отдельный лог-канал `hh`;
- условные запросы к справочникам (`If-None-Match`), кэш в Redis + таблица `hh_dictionaries`.

### 4.3. Приёмник вебхуков

- `POST /api/hh/webhooks/:secret` — **вне** `authenticate`, вне общего `apiRateLimiter` (собственный лимитер), без CSRF;
- проверка секрета сравнением с постоянным временем; неизвестный секрет → 404 без деталей;
- проверка `id` на дубликат → `409 Conflict` (как требует hh);
- запись сырого события в `hh_webhook_events` со статусом `received`, немедленный `200`;
- фоновый воркер разбирает события по `action_type` (см. 2.5), помечает `processed` / `failed` + `error`, ретраит `failed` с бэкоффом до 5 раз, затем `dead` + уведомление администратору;
- метрики: количество по типам, лаг обработки, доля ошибок → `/health/hh`.

### 4.4. Фоновая синхронизация (`hh-sync.service`)

Вебхуки не гарантируют доставку, поэтому периодическая сверка обязательна.

**Предварительная доработка планировщика (входит в объём работ).** Текущий `backend/src/services/scheduler.ts` — не планировщик общего назначения: это один тик с очередью `email-scheduler`, единственным обработчиком `runScheduledEmails()` и общим для всех периодом `SCHEDULER_INTERVAL_MINUTES` (cron `*/N * * * *`). Расписания из таблицы ниже в эту модель не ложатся. Требуется расширить `scheduler.ts` реестром задач: регистрация задачи по имени с собственным cron-выражением, блокировка от повторного запуска по имени, единый учёт результатов. Существующее поведение email-рассылок и локальный fallback при `SCHEDULER_USE_QUEUE=false` должны сохраниться без изменений.

| Задача | Периодичность | Содержание |
|---|---|---|
| `hh:vacancies` | каждые 15 мин | активные (`.../vacancies/active`, per_page 50), архивные и скрытые за период; upsert в `hh_vacancies`; выставление `is_deleted` для исчезнувших |
| `hh:negotiations` | каждые 10 мин | по каждой активной вакансии — коллекции `GET /negotiations?vacancy_id=...` и списки коллекций; upsert `hh_negotiations` по `topic_id`; фиксация `employer_state`, `applicant_state`, `has_updates` |
| `hh:vacancy-stats` | 1 раз в сутки, 03:00 | `GET /vacancies/{id}/stats` по активным вакансиям — просмотры/отклики для отчётности |
| `hh:dictionaries` | 1 раз в сутки, 03:20 | `/dictionaries`, `/areas`, `/professional_roles`, `/languages`, `/skills`, `/industries` с `ETag` |
| `hh:employer-meta` | 1 раз в сутки, 03:30 | менеджеры, адреса (`changed_after`), подразделения, тесты, брендированные шаблоны, шаблоны писем |
| `hh:services` | каждые 6 ч | `method_access`, `payable_api_actions/active`, `limits/resume`, `available_types` |
| `hh:token-health` | каждый час | проверка `GET /me`, срок жизни токена, статус подписок вебхуков |

Требования:
- каждый запуск фиксируется в `hh_sync_runs` (тип, начало, конец, статус, счётчики, текст ошибки);
- задача не запускается повторно, если предыдущая ещё выполняется (блокировка по типу);
- работает и в режиме `SCHEDULER_USE_QUEUE=false` (локальный fallback планировщика — как в текущей реализации);
- при `needs_reauth` / `captcha_required` фоновые задачи приостанавливаются, чтобы не выжигать лимиты.

### 4.5. Вакансии в Report

Раздел `/hr/vacancies` — реестр в корпоративном табличном виде (см. раздел 5).

Колонки реестра: № / название / регион / профроль / ответственный менеджер / тип публикации / статус (`черновик`, `на модерации`, `опубликована`, `архив`, `скрыта`) / дата публикации / дата окончания / осталось дней / просмотры / отклики (всего · новых) / рекрутер Report.

Возможности:
1. **Создание черновика** — мастер в 4 шага (аналог `ContractWizard`: `Dialog` с текущим шагом в состоянии компонента; готового степпера MUI в проекте нет и вводить его не обязательно): «Основное» (название, регион, профроли, тип занятости, график, опыт) → «Условия» (зарплатный диапазон, режим, частота выплат, формат работы, адрес из справочника адресов компании) → «Описание» (визуальный редактор HTML, ключевые навыки, тест, брендированный шаблон) → «Публикация» (`vacancy_properties`, `closed_for_applicants`, ответственный менеджер, контакты, проверка квоты по `available_types`).
   - валидация полей — по `GET /vacancy_conditions` до отправки, чтобы не ловить `bad_json_data`;
   - сохранение как черновик hh (`POST /vacancies/drafts`) либо как локальный черновик Report, если квота черновиков исчерпана (`429`);
   - проверка дублей: при `vacancies / duplicate` показать найденные вакансии из `items[]` и предложить «Опубликовать всё равно» (`ignore_duplicates=true`).
2. **Публикация** — `POST /vacancies` (или `POST /vacancies/drafts/{id}/publish`). После публикации показать предупреждение о ручной модерации hh.
3. **Редактирование** — `PUT /vacancies/{id}`; составные поля отправляются целиком. Поля `vacancy_properties`, `billing_type` и `manager` меняются **тремя отдельными запросами**, каждый со своим единственным обязательным полем (см. 2.4). В UI это отдельная форма «Тип публикации и ответственный», которая последовательно отправляет только изменённые из трёх.
4. **Продление** — сначала `GET /vacancies/{id}/prolongate` (условия и причина недоступности из справочника `vacancy_not_prolonged_reason`), затем `POST`. В реестре — индикатор «осталось дней» с подсветкой ≤ 3 дней.
5. **Архивация** — `PUT /employers/{employer_id}/vacancies/archived/{vacancy_id}` с подтверждением.
6. **Восстановление из архива** — «Опубликовать заново»: форма предзаполняется из архивной вакансии, отправляется `POST /vacancies` с `previous_id` (все остальные поля передаются заново). В UI явно указывается, что это новая публикация со списанием услуги. Связь новой вакансии со старой подтверждается полем `previous_vacancy_id` в вебхуке `VACANCY_PUBLICATION_FOR_VACANCY_MANAGER` — по нему цепочка публикаций склеивается в отчётности (иначе срок закрытия вакансии обнулится при каждой переподаче).
7. **Скрытие/восстановление** — `PUT` / `DELETE .../vacancies/hidden/{vacancy_id}`.

Карточка вакансии (`/hr/vacancies/:id`): шапка со статусом и сроками, вкладки «Описание», «Отклики» (воронка по этой вакансии), «Статистика» (просмотры/отклики/конверсия), «История» (изменения, продления, из аудита и вебхуков).

### 4.6. Воронка подбора и карточка кандидата

**Собственная воронка Report** (таблица `hh_pipeline_stages`, настраивается администратором, значения по умолчанию):

| Код этапа Report | Название | Целевое `resulting_employer_state` в hh |
|---|---|---|
| `new` | Новый отклик | `response` |
| `screening` | Первичный отбор | `consider` |
| `phone_interview` | Телефонное интервью | `phone_interview` |
| `interview` | Собеседование | `interview` |
| `assessment` | Оценка / тестирование | `assessment` |
| `offer` | Оффер | `offer` |
| `hired` | Принят | `hired` |
| `rejected` | Отказ | `discard_by_employer` (шаблон письма — `discard` либо `discard_after_interview` из `/employers/{id}/mail_templates`) |
| `reserve` | Резерв | нет перехода, остаётся в текущем состоянии hh |

Правила:
- набор состояний hh почти совпадает с предлагаемой воронкой (собственными остаются только `screening` в части внутренних под-шагов и `reserve`), поэтому маппинг делается 1:1 везде, где это возможно, и расхождение минимально;
- значения целевых состояний **не хардкодятся**: `hh_pipeline_stages.target_employer_state` заполняется администратором из фактически встреченных `resulting_employer_state`; при первом подключении список собирается из `actions[]` по реальным откликам;
- каждому этапу задаётся целевое состояние и признак «синхронизировать в hh»;
- переход в hh выполняется через `actions[].url` + `arguments` из свежего ответа API по этому отклику; перед действием отклик перечитывается;
- если целевое действие в `actions[]` отсутствует — перевод внутри Report выполняется, в карточке показывается предупреждение «Статус в hh не изменён: действие недоступно», событие пишется в аудит;
- обратная синхронизация: `NEGOTIATION_EMPLOYER_STATE_CHANGE` (кто-то изменил статус в кабинете hh) — этап в Report обновляется по маппингу, в истории отмечается источник `hh`;
- при конфликте (изменения с обеих сторон в пределах окна синхронизации) приоритет у более позднего `transferred_at`; оба события остаются в истории.

**Экран `/hr/candidates`** — два режима отображения, переключатель в шапке:
- **Таблица** (по умолчанию, корпоративный плотный реестр): кандидат / вакансия / этап / дата отклика / дней в этапе / источник / рекрутер / последнее действие;
- **Канбан** — колонки по этапам с drag-and-drop, счётчиками и суммарным «днями в этапе»; массовые действия с учётом лимита 50 `topic_id` за запрос **и требования hh, что все отклики в одном запросе принадлежат одной вакансии** — выборка сначала группируется по `vacancy_id`, затем режется на пачки по 50.

Фильтры: вакансия, этап, рекрутер, период отклика, «только новые», «с обновлениями», регион, наличие открытых контактов.

**Карточка кандидата** (модальное окно с вкладками, по образцу карточки договора):
- **Резюме** — данные из `GET /resumes/{resume_id}`: должность, опыт, образование, навыки, зарплатные ожидания, регион, гражданство; кнопка «Скачать PDF» (через прокси Report, ссылка из `download`); при `can_view_full_info: false` — заметная плашка «Полный просмотр недоступен»;
- **Контакты** — по умолчанию скрыты; кнопка **«Открыть контакты»** с диалогом подтверждения и текстом о списании контакта; перед вызовом проверяются `hidden_fields`, и если нужное поле скрыто — кнопка блокируется с пояснением (не тратим контакт впустую); после открытия контакты показываются и кэшируются на срок из настройки ретенции;
- **Процесс** — таймлайн этапов (кто, когда, из какого в какой, источник Report/hh), кнопки перевода, «Пригласить», «Отказать» (с выбором шаблона из `mail_templates` и обязательным комментарием при отказе после интервью);
- **Интервью** — список запланированных/проведённых (см. 4.7);
- **Заметки** — внутренние комментарии рекрутеров и нанимающего руководителя, с упоминаниями `@` (по образцу `ContractDiscussionPanel`); хранятся только в Report;
- **Переписка** — чат через `/common/chats/{chat_id}/messages` (`chat_id` из вебхука или из отклика): чтение истории, отметка прочитанным, отправка текстового сообщения. Вложения в v1 не отправляются — кнопка ведёт в кабинет hh по `alternate_url`. Устаревшие `/negotiations/{nid}/messages` не используются;
- **Тест** — результаты `GET /negotiations/{nid}/test/solution`, если по вакансии назначен тест.

Пометка отклика прочитанным — `POST /negotiations/read` при открытии карточки; при массовой пометке батчи формируются по правилу «одна вакансия + ≤ 50 `topic_id`».

### 4.7. Интервью

Внутренняя сущность Report (в hh не передаётся, кроме текста приглашения):
- планирование: дата/время (в таймзоне пользователя), длительность, тип (телефон / видео / офис), место или ссылка, участники из пользователей Report;
- при создании — email участникам через существующий SMTP-сервис и приглашение кандидату отдельным действием hh (`POST /negotiations/phone_interview` либо действие из `actions[]` с сообщением);
- результат: `состоялось` / `не пришёл` / `перенесено` / `отменено`, оценка (1–5), заключение (текст), рекомендация «дальше/отказ»;
- напоминание участникам за 60 минут (через scheduler);
- отображение в разделе `/hr/interviews` — недельная сетка + список, и в БП-дашборде как задача.

### 4.8. Уведомления

Email (через существующий `EmailService` / SMTP-настройки):
- новый отклик по вакансии → ответственному рекрутеру (дайджест: не чаще 1 письма в 15 минут, агрегируя отклики);
- назначено интервью / изменено / отменено → участникам;
- вакансия снята с публикации / истекает через 3 дня → ответственному рекрутеру и `head_hr`;
- ошибка подключения (`needs_reauth`, `captcha_required`, блокировка подписки вебхуков) → `admin`;
- остаток пакета `API_LIMITED` < 10% → `admin` и `head_hr`;
- еженедельный дайджест по подбору → `head_hr`, `general_director`.

Дайджест использует существующий механизм `email_schedules`, но это **не сводится к добавлению строки в справочник**: в `backend/src/services/email-scheduler.service.ts` `ReportType` — закрытый union (`'sv_pdf' | 'planning_v2_segment' | 'monthly_final'`), а `normalizeReportType()` молча схлопывает неизвестные значения в `planning_v2_segment` — то есть незарегистрированный тип не упадёт с ошибкой, а отправит чужой отчёт. В объём работ входит: расширение union значением `hh_recruiting_weekly`, ветка в `normalizeReportType()` и в `processScheduledEmails()`, а также определение значения обязательного поля `department` (`varchar(50)`, NOT NULL) для HR-рассылок — предлагается зарезервированное `HR`.

Все письма содержат deep link на конкретную карточку (по образцу договоров: сохранение `returnTo` при логине).

WebSocket (существующий `websocket.service`): счётчик новых откликов и непрочитанных заметок в левом меню — по образцу `contract-unread-store`.

### 4.9. Отчётность

Раздел `/hr/reports`, экспорт в Excel (существующий подход `exceljs`; **не использовать `xlsx`** — в проекте уже зафиксирована известная уязвимость без фикса).

Отчёты:
1. **Воронка подбора** за период: количество на каждом этапе, конверсия этап→этап, в разрезе вакансии/подразделения/рекрутера.
2. **Срок закрытия вакансии** (time-to-hire, time-to-first-response): среднее и медиана, по вакансиям и подразделениям.
3. **Источники и качество**: сколько откликов, сколько дошло до интервью, сколько отказов и по каким причинам.
4. **Нагрузка рекрутеров**: активные вакансии, кандидаты в работе, среднее время реакции на отклик, «индекс вежливости» из `negotiations_statistics`.
5. **Расходы на публикации**: количество публикаций и продлений по типам за период, потребление пакета API.
6. **Статистика вакансий** из `/vacancies/{id}/stats`: просмотры → отклики → приглашения.

Виджеты для существующего **SW Tech Dashboard**: «Открытых вакансий», «Кандидатов в работе», «Средний срок закрытия», «Просрочено реакций > 3 дней» — карточки с drill-down в `/hr/...` по образцу текущих карточек направлений.

Внимание на права: текущий `canViewTechDashboard` включает **`head_sales`** (`admin | director | general_director | financer | head_sales`), а по матрице 4.10 у `head_sales` доступа к модулю нет. Чтобы не открыть HR-данные непреднамеренно, HR-виджеты выводятся под отдельным предикатом `canViewHrReports`, а не под `canViewTechDashboard`.

### 4.10. Роли и доступ

Новые роли **не заводятся** — используются существующие из `ROLE_VALUES`:

| Роль | Права в модуле |
|---|---|
| `admin` | всё, включая вкладку настроек интеграции, пересоздание подписок, настройку этапов воронки |
| `head_hr` | вакансии (создание, публикация, продление, архив), все кандидаты, интервью, отчёты, назначение ответственного рекрутера |
| `hr_recruiter` | вакансии, где он ответственный (чтение всех); кандидаты по своим вакансиям — полный цикл, включая открытие контактов; интервью; свои отчёты |
| `hr_specialist` | чтение вакансий и кандидатов, планирование и проведение интервью, заметки; без публикации вакансий и без открытия контактов |
| `general_director`, `director`, `financer` | только отчётность и виджеты дашборда; без доступа к ПДн кандидатов (ФИО и контакты не отображаются, кандидат обезличен до «Кандидат #N») |
| остальные роли | доступа нет |

Реализация:
- новые предикаты в `frontend/src/utils/rolePermissions.ts`: `canAccessHrCabinet`, `canManageHrVacancies`, `canViewHrCandidatePii`, `canOpenHrContacts`, `canViewHrReports`, `canManageHrIntegration`;
- зеркальная проверка на backend через `authorizeRole(...)` и отдельный `hh-access.service` (по образцу `contract-approval-access.service`) — фронтовые предикаты не являются защитой;
- открытие контактов дополнительно требует, чтобы у подключённого менеджера hh было право `can_view_resume_contacts`, иначе кнопка недоступна с пояснением;
- каждое действие с ПДн (просмотр резюме, открытие контактов, скачивание PDF) пишется в существующий `audit_logs` с указанием пользователя, `resume_id`, вакансии и результата.

## 5. Вид и интерфейс (корпоративный стиль)

Модуль обязан выглядеть как часть существующей системы, а не как отдельный продукт. Опорные образцы в коде: `ContractApprovalPage` + `styles/contract-approval.css` (реестры и карточки), `SWTechDashboardPage` + `sw-tech-dashboard.css` (шапка с периодом и карточки), `WarehousePage` (панели-вкладки).

### 5.1. Общие правила

- **Стек:** React 18 + TypeScript, MUI, Zustand, Recharts, React Router 6 — без новых UI-библиотек. Канбан — на существующих примитивах MUI + HTML5 drag-and-drop либо `@dnd-kit` (единственная допустимая новая зависимость фронта, обосновать при согласовании).
- **Плотность:** реестры — как `contract-registry-table`: шрифт 10–11 px, padding ячеек `6px 8px`, `white-space: nowrap` с `text-overflow: ellipsis`, залипающая шапка, границы `1px solid #d0d7de`, горизонтальный скролл контейнера.
- **Палитра** — из существующих стилей, без новых цветов: фон акцентных панелей `#f7faff` / `#f8fbff`, рамки `#c9d7ec` / `#dbe4ef` / `#d0d7de`, основной текст `#27364b` / `#314158`, вторичный `#566579` / `#64748b`; статусы — «ожидание» `#fff7e6` / `#9a5b00`, «успех» `#e8f5e9` / `#2e7d32`, «отказ» — красная гамма MUI `error`.
- **Статусы** — текстом, компактными плашками `border-radius: 999px`, `padding: 2px 8px`, `font-size: 10px`, `font-weight: 700` (как `.contract-secretary-task-status`; `uppercase` там **не применяется** — верхний регистр в образце используется только для подписей-caption и кнопок). Не злоупотреблять цветными чипами в таблицах — служебные статусы выводятся простым текстом.
- **Карточки открываются двойным кликом по строке реестра** — правило, уже принятое в модуле склада; одиночный клик выделяет строку.
- **Панель периода** — синяя шапка с выбором периода как на SW Tech Dashboard, для отчётных экранов.
- **Задачи пользователя** — блок «Моя задача» вверху экрана по образцу `contract-my-task`: сетка `auto / 210px / minmax(260px,1fr) / auto`, компактные кнопки высотой 26–40 px.
- **Локализация** — весь интерфейс на русском; даты — в таймзоне пользователя (`users.timezone`), денежные значения — с разделителями разрядов.
- **Пустые состояния и деградация** — при `needs_reauth`, `captcha_required`, `402 требуется платный доступ` экран не «падает»: показывается баннер с понятным текстом и, для админа, ссылкой в настройки интеграции.

### 5.2. Навигация

В `DashboardLayout` добавляется раздел левого меню **«Кабинет HR»** — раскрывающийся toggle-пункт, с сохранением состояния раскрытия в `localStorage` (как «Показатели» и «График работы»):

```
Кабинет HR
├── Обзор                 /hr/dashboard
├── Вакансии              /hr/vacancies
├── Кандидаты             /hr/candidates        [бейдж: новых откликов]
├── Интервью              /hr/interviews        [бейдж: сегодня]
└── Отчёты по подбору     /hr/reports
```

Настройки интеграции живут не в меню, а вкладкой на `/settings` (только `admin`).

**Стартовые страницы — изменение существующего поведения, требует согласования.** Сейчас в `routes/defaultAuthenticatedRoute.ts`: `head_hr` и `hr_specialist` попадают на `/operations-preview?location=ktk_vvo&section=containers` (график работы), а `hr_recruiter` — на `/business-processes/dashboard` (он ведёт БП «Проверка кандидатов»). Предлагается: `head_hr` → `/hr/dashboard`, `hr_recruiter` и `hr_specialist` → `/hr/candidates`. Прежние разделы остаются доступны через меню и не удаляются; вопрос вынесен в раздел 11 — если для HR приоритетнее график работы или БП-дашборд, стартовые страницы не меняем и ограничиваемся пунктом меню.

### 5.3. Экраны

**`/hr/dashboard` — обзор подбора.** Синяя шапка с периодом. Ряд карточек (в стиле карточек направлений SW Tech Dashboard, с drill-down): «Открытых вакансий», «Новых откликов за период», «Кандидатов в работе», «Интервью на неделе», «Средний срок закрытия», «Просрочено реакций». ## 8. Нефункциональные требования и риски

### 8.1. Надёжность и деградация

- Недоступность hh **не должна ронять Report**: все экраны модуля работают на локальных данных, действия записи возвращают понятную ошибку и предлагают повтор.
- Circuit breaker на исходящие запросы к hh (по образцу `utils/db-circuit.ts`): после N подряд ошибок 5xx/таймаутов — пауза, статус в `/health/hh`.
- Все фоновые задачи идемпотентны и безопасны для повторного запуска.
- Приёмник вебхуков укладывается в таймаут hh (5 с) с большим запасом — целевое время ответа < 1 с при любой нагрузке (только запись + ответ).

### 8.2. Персональные данные и соглашение hh (152-ФЗ)

Из соглашения разработчика hh (`https://dev.hh.ru/admin/developer_agreement`), дословно:

> «Посредством Приложения не должно быть возможным скачивание (получение, извлечение) данных для формирования другой базы данных»
> «Разработчик Приложения обязан следить за актуальностью вышеуказанных материалов, в том числе, своевременно удалять вакансии, которые перемещены в архив»
> «Разработчик приложения несет ответственность за использование, сохранность и конфиденциальность полученного им уникального API-ключа»
> «HeadHunter вправе в любое время … приостановить возможность использования всего Сервиса … или отдельных его функций, действие уникального API-ключа»

Отсюда обязательные ограничения проекта:

1. **Не создавать копию базы резюме.** Хранятся `hh_resume_id`, `topic_id`, внутренние этапы, заметки и обезличенный слепок (опыт/навыки/образование). ФИО и контакты хранятся только по кандидатам, с которыми ведётся работа, и только после открытия контактов.
2. **Ретенция.** `HH_PII_RETENTION_DAYS` (по умолчанию 180). По истечении — автоматическое обезличивание записи (`display_name`, `contacts_json_enc`, PDF удаляются, остаются идентификаторы и агрегаты для отчётности). Отчётность строится на обезличенных агрегатах и после очистки не ломается.
3. **Ручное удаление.** Администратору доступно удаление ПДн конкретного кандидата с сохранением статистики.
4. **Шифрование.** Контакты и токены — AES-256-GCM; PDF резюме — в отдельном каталоге вне статики, отдача только через авторизованный прокси.
5. **Ограничение видимости.** Роли `director`, `general_director`, `financer` видят кандидатов обезличенно.
6. **Аудит.** Каждый просмотр резюме, открытие контактов и скачивание PDF — в `audit_logs`.
7. **Архивные вакансии** снимаются с внутренних витрин при получении `VACANCY_ARCHIVATION` — как требует соглашение.
8. **Локализация БД** — PostgreSQL размещается на территории РФ (ст. 18 ч. 5 152-ФЗ). Требуется подтвердить для площадки Amvera.
9. Перед вводом в эксплуатацию — **юридическая проверка**: политика обработки ПДн компании дополняется разделом о рекрутинге, назначается ответственный, фиксируются сроки хранения. Полный текст соглашения разработчика hh должен прочитать юрист компании.

| Платный доступ к API не куплен | все методы откликов и резюме недоступны | заложить в этап 0 покупку через персонального менеджера hh; до этого — работа на моках, UI полностью разрабатывается |

| Изменение логики коллекций и действий на стороне hh | ломаются переводы этапов | работать только через `actions[]` из ответа; контрактные тесты; алерт при отсутствии ожидаемого действия |
| Миграция hh со старого API сообщений на `/common/chats` | сломается переписка, если использовать устаревшие методы | использовать только `/common/chats/*`; устаревшие `/negotiations/{nid}/messages` не применять |
| Недокументированный троттлинг hh (403/429/капча) | зависание синхронизации | очередь с rate-limit, бэкофф, приоритет пользовательских действий, статус в health |
| Потеря пары токенов при гонке обновления | ручная переавторизация | блокировка на обновление, атомарное сохранение, алерт `needs_reauth` |
| Блокировка подписки вебхуков из-за медленного приёмника | тихая потеря событий | приёмник только пишет и отвечает; периодическая сверка как страховка; мониторинг |
| Отсутствие подписи вебхуков у hh | подделка событий | секрет в URL ≥ 32 символа, возможность перевыпуска, allowlist IP при наличии, идемпотентность |
| Хранение резюме = «другая база данных» по соглашению hh | риск отзыва ключа | минимизация хранения, ретенция, обезличивание (8.2) |
| Глубина выдачи 2000 | неполные выгрузки | сужение фильтров по датам и вакансиям вместо глубокой пагинации |
| Спецификация hh может измениться | расхождение с ТЗ | зафиксировать `hh-openapi.yaml` в репозитории, сверять при каждом релизе |

### 8.4. Производительность

- Реестры — серверная пагинация, 50 строк на страницу, индексы по `vacancy_id`, `stage_code`, `responsible_user_id`, `first_response_at`.
- Канбан — ограничение 200 карточек на колонку с догрузкой.
- Отчёты за период > 6 месяцев считаются из суточных агрегатов (`hh_vacancy_stats` + материализованные срезы), а не по «сырым» откликам.

## 9. Этапы и приоритеты

**Этап 0 — организационный (параллельно разработке, старт немедленно)**
Регистрация приложения на dev.hh.ru, согласование названия и логотипа, подписание соглашения разработчика; запрос персональному менеджеру hh на подключение платного доступа к API для `employer_id` компании; юридическая проверка обработки ПДн. Скачивание и фиксация спецификации в репозитории.

**Этап 1 — фундамент (без ПДн)**

**Этап 2 — вакансии**
Синхронизация вакансий, реестр, карточка, мастер создания, публикация, редактирование, продление, архив/скрытие, повторная публикация, статистика. Критерий: рекрутер ведёт полный жизненный цикл вакансии из Report.

**Этап 3 — отклики и воронка**

**Этап 4 — интервью и отчётность**
Интервью, напоминания, отчёты, Excel-выгрузки, виджеты SW Tech Dashboard, еженедельный дайджест. Критерий: руководитель видит воронку, срок закрытия и нагрузку рекрутеров без ручной сборки.

Поиск по базе резюме и сохранённые поиски (платно), заявки на подбор с согласованием, связка с БП «Проверка кандидатов», второй job-борд.

## 10. Критерии приёмки (ключевые)

1. Ни один исходящий запрос к hh не уходит без `User-Agent`/`HH-User-Agent`; тест подтверждает 400 при попытке обхода клиента.
2. `access_token` обновляется только после истечения; параллельный запуск двух воркеров не приводит к `token has already been refreshed` (нагрузочный тест на 10 параллельных обновлений).
3. Приёмник вебхуков отвечает 2xx за < 1 с при 100 событиях/мин (таймаут hh — 5 с); повторное событие с тем же `id` → `409`, дубликат в БД не создаётся. Обрабатываются все 9 типов событий, включая `CHAT_CREATED` и `CHAT_MESSAGE_CREATED`.
4. Все переводы этапов выполняются через `actions[].url` из свежего ответа, целевые состояния берутся из `resulting_employer_state`; в коде отсутствуют захардкоженные URL действий, имена коллекций и списки состояний (проверяется ревью + тест).
5. Массовые операции не отправляют более 50 `topic_id` за запрос и не смешивают отклики разных вакансий в одном запросе; выделение 200 кандидатов по 3 вакансиям корректно разбивается на батчи «одна вакансия + ≤ 50».
6. Открытие контактов невозможно без явного подтверждения; при `hidden_fields`, скрывающих запрошенное поле, действие блокируется до вызова API; каждое списание попадает в `hh_contact_charges` и `audit_logs`.
7. Роли `director`, `general_director`, `financer` не получают ФИО и контакты кандидатов ни в одном ответе API (проверяется интеграционным тестом на все маршруты `/api/hh/*`).
8. Публикация, продление, архивация, скрытие и повторная публикация вакансии подтверждены на реальном аккаунте: состояние в кабинете hh совпадает с состоянием в Report после синхронизации.
9. Отключение hh (эмуляция 503 и таймаутов) не приводит к ошибкам на экранах модуля; действия записи возвращают понятное сообщение; `/health/hh` показывает `DOWN`.
10. По истечении `HH_PII_RETENTION_DAYS` кандидат обезличивается автоматически, отчёты за прошлые периоды при этом считаются корректно.
11. Отчёт «Воронка подбора» за месяц совпадает с ручным подсчётом по контрольной выборке из 3 вакансий.
12. Экраны модуля визуально соответствуют разделу 5: плотность таблиц, палитра, открытие карточек двойным кликом, toggle-меню с сохранением состояния в `localStorage`.

## 11. Открытые вопросы

1. **Юридическое лицо и аккаунт.** Под каким `employer_id` работает компания на hh; один аккаунт или несколько (например, отдельные для Владивостока и Москвы)? От этого зависит, включать ли мультиподключение в v1.
2. **Кто подключает.** Есть ли менеджер hh с админ-правами (`has_admin_rights`), от имени которого будет выдан токен? Без админ-прав часть методов недоступна.
3. **Тариф hh.** Действует ли поконтактная модель (списание за открытие контактов) или безлимитный доступ к базе? Нужен ли внутренний суточный лимит открытий на рекрутера и какой.
4. **Этапы воронки.** Предложенные 8 этапов (4.6) — черновик. Нужен согласованный с HR перечень, включая причины отказа (справочник для отчётности).
5. **Ответственные.** Как распределяются вакансии между рекрутерами — вручную `head_hr` или по подразделению/направлению?
6. **Подразделения.** Нужно ли связывать вакансии с направлениями планирования (`KTK_VVO`, `AUTO`, `RAIL`…) для сквозной отчётности «план по персоналу ↔ найм»?
7. **Ретенция ПДн.** Согласовать срок хранения (предложено 180 дней) и порядок ручного удаления по запросу кандидата.
8. **Связка с БП «Проверка кандидатов».** В v1 не делается по решению заказчика. Зафиксировать как отдельную доработку этапа 5 или отказаться совсем.
9. **Другие площадки.** Планируется ли Avito Работа / SuperJob? Если да — уточнить, закладывать ли абстракцию провайдера сразу (стоимость ~10–15% к этапам 2–3).
10. **Оффер и приём на работу.** Нужен ли внутри модуля этап оформления оффера с шаблоном документа, или это остаётся вне системы.
11. **Стартовые страницы HR-ролей.** Менять ли текущие точки входа (`head_hr` / `hr_specialist` — график работы, `hr_recruiter` — БП-дашборд) на разделы кабинета HR, или оставить как есть и ограничиться пунктом меню (см. 5.2).
12. **Объём чата.** Достаточно ли в v1 текстовой переписки без вложений, или вложения (`/common/chats/files/*`) нужны сразу — это ~1 неделя к этапу 3.
13. **Отмена старого плана.** Подтвердить, что `plans/PLAN_HH_INTEGRATION.md` замещается настоящим ТЗ и его контракт (`hh_accounts`, `GET /api/hh/callback`, `HH_TOKEN_ENC_KEY`) не используется.

# 12. HR-ТЗ «SimpleHR»: требования заказчика и их соотношение с модулем

Источник: техническое задание «Разработка системы автоматизации подбора персонала», проект **SimpleHR**, заказчик Прямушко Е.Н.

Цель заказчика сформулирована шире, чем интеграция с hh.ru: централизованно вести весь цикл рекрутинга — от открытия вакансии до выхода сотрудника на работу, включая кадровый резерв, аналитику и интеграции (HeadHunter, Фарпост).

## 12.1. Роли в терминах HR-ТЗ

| Роль HR-ТЗ | Роль в Report | Права по HR-ТЗ |
|---|---|---|
| Руководитель подразделения | `manager_*` / `head_*` профильного направления | создание заявок на подбор |
| Специалист по подбору персонала | `hr_recruiter` | привязка кандидатов к заявкам, приглашения на телефонное интервью, на собеседование с заказчиком (очное и онлайн), отклонение с обязательной причиной |
| Руководитель отдела персонала | `head_hr` | просмотр кандидатов и комментариев, согласование, назначение собеседований, отклонение, все вакансии, аналитика, отчёты, полный доступ |

Расхождение с разделом 4.10: HR-ТЗ вводит **руководителя подразделения как активного участника процесса** (автор заявки и участник согласования кандидата). В текущей матрице прав такие роли доступа к модулю не имеют. Это нужно добавить — задачи 29 и 30 бэклога.

## 12.2. Этапы подбора по HR-ТЗ

Новый отклик → Скрининг → Телефонное интервью (специалист по подбору) → Руководитель подразделения → Очное интервью с заказчиком → Оффер → Принят или отказ.

Реализованная воронка совпадает по смыслу; коды этапов в коде: `new`, `screening`, `phone_interview`, `submitted_to_manager`, `manager_interview`, `offer`, `hired`, `rejected`. Это отличается от чернового перечня раздела 4.6 (там были `interview`, `assessment`, `reserve`) — **источником истины считать реализованные коды**, они ближе к формулировкам заказчика. Кадровый резерв реализован как статус кандидата (`status = reserve`), а не как этап, — это осознанное решение: кандидат в резерве сохраняет последний достигнутый этап.

## 12.3. Карточка кандидата по HR-ТЗ

Требуется единый цифровой профиль без переключения вкладок:

- главная панель: ФИО, фотография, желаемая должность, зарплатные ожидания, ключевые контакты (телефон, email, мессенджеры);
- статус и воронка: наглядный индикатор текущего этапа;
- вкладка «Резюме»: оригинальный текст, автоматически распознанный и структурированный при импорте со сторонних сайтов;
- история и события: хронологическая лента — письма, результаты телефонных интервью, запланированные встречи, прикреплённые файлы (тестовые задания, сканы);
- оценки и комментарии: фидбек рекрутера и нанимающих менеджеров, результаты тестов и опросов.

Реализовано: главная панель, статус, распознанный текст резюме, история событий, комментарии. Не реализовано: фотография (поле в БД есть, не заполняется), вложения файлов к кандидату, структурированные оценки и результаты тестов.

## 12.4. Требования, выполнимые не для всех площадок

HR-ТЗ формулирует два требования как общие, но технически они относятся только к hh.ru:

1. **«Автоматическая публикация: одной кнопкой публикуется сразу везде (HeadHunter, Фарпост)»** — по FarPost публикация остаётся в кабинете площадки. В Report фиксируются факт публикации и ссылка.
2. **«Каждые 5 минут система должна получать новые отклики»** — по hh.ru это вебхуки плюс периодическая сверка (для откликов hh достаточно интервала 10 минут, вебхуки дают доставку почти сразу). По FarPost автоматического получения откликов не будет: импорт инициирует рекрутер.

Обоснование — в `FARPOST_API_RESEARCH.md`. Эти ограничения нужно зафиксировать в договорённостях с заказчиком до сдачи, чтобы они не выглядели невыполненными требованиями.

## 12.5. Дополнительные требования HR-ТЗ, которых нет в разделах 1–11

| Требование | Где в бэклоге |
|---|---|

Решение: полнотекстовый поиск ведётся **только** по кандидатам, которые сами откликнулись, были импортированы рекрутером с FarPost или введены вручную. Резюме, полученные через платный поиск по базе hh.ru, в локальную базу не складываются и в поиске не участвуют. Это разделение нужно закрепить полем источника и проверять в тестах.
