# Модуль подбора: модель доступа и обработка персональных данных

Дата: 30.07.2026

## 1. Почему модель именно такая

В системе исторически есть три «HR-подобные» роли, и они относятся к **разным службам**:

| Роль | Служба | Что делает в системе |
|---|---|---|
| `head_hr` | Отдел кадров (кадровое администрирование) | графики работы, отчёты по графикам. **К подбору отношения не имеет** |
| `hr_specialist` | Отдел кадров | то же |
| `hr_recruiter` | Подбор персонала | БП проверки кандидатов + модуль подбора |

Роли `head_hr` и `hr_specialist` уже работают в продакшене со своими функциями. **Коды ролей сознательно не переименовывались:** они встречаются в 14 файлах и в работающем функционале, переименование потребовало бы миграции данных и перелогина пользователей, а дало бы только косметику. Вместо этого:

- смысл ролей закреплён в комментариях `backend/src/constants/hh.ts` и в этом документе;
- в админке стоит поправить подписи ролей так, чтобы служба читалась однозначно (например «Отдел кадров: руководитель» вместо «Руководитель отдела кадров»).

## 2. Права модуля

Права заданы **именованными capability**, а не разрозненными списками ролей. Списки живут в одном месте — `backend/src/constants/hh.ts`, проверка — в `backend/src/services/hh-access.service.ts`. Причина: «подать заявку на подбор» может почти любой руководитель, и перечислять роли в каждом месте нельзя.

| Capability | Кто | Что даёт |
|---|---|---|
| `hr.recruiting` | `admin`, `hr_recruiter` | кандидаты, вакансии, воронка, интервью, импорт |
| `hr.pii.view` | `admin`, `hr_recruiter` | ФИО, контакты, фото, тексты резюме |
| `hr.vacancy.manage` | `admin`, `hr_recruiter` | создание и изменение вакансий и кандидатов |
| `hr.reports.view` | `admin`, `hr_recruiter` | отчётность (директорам подключим отдельно и без ПДн) |
| `hr.integration.manage` | `admin` | настройки интеграции с площадками |
| `hr.request.create` | руководители и директора | подать заявку на подбор |
| `hr.request.review` | руководители и директора | рассматривать кандидатов по своей заявке |

Список руководителей-заявителей (`HH_REQUESTER_ROLES`): `general_director`, `director`, `head_sales`, `head_ktk_vvo`, `head_ktk_mow`, `head_hr`, `garage_head`, `garage_head_vvo`, `warehouse_manager`, `warehouse_manager_vvo`, `security`, `chief_accountant`. Рядовые менеджеры (`manager_*`) заявки не подают.

`head_hr` попадает в этот список как руководитель службы: подбор себе в отдел кадров он заказывает так же, как любой другой руководитель, но доступа к базе кандидатов у него нет.

Клиентские предикаты в `frontend/src/utils/rolePermissions.ts` дублируют эти списки, но служат только для скрытия UI — решение всегда принимает сервер.

## 3. Процесс

```
Руководитель                        Рекрутер                        Руководитель
    │                                   │                                │
    ├─ создаёт заявку на подбор ───────►│                                │
    │   (маршрута согласования нет:     │                                │
    │    создал — рекрутер увидел)      │                                │
    │                                   ├─ берёт в работу                │
    │                                   ├─ ищет кандидатов               │
    │                                   ├─ отправляет отобранных ───────►│
    │                                   │                                ├─ смотрит профили
    │                                   │◄─── «берём» / «не подходит» ───┤   и решает
    │                                   │      (при отказе комментарий   │
    │                                   │       обязателен)              │
    │                                   ├─ ведёт одобренных дальше       │
    │                                   │   по воронке                   │
```

Автор заявки видит **только свою заявку**. Чужие заявки не открываются даже другому руководителю — в них персональные данные кандидатов (`loadRequestForViewer` в `hh-hiring-request.service.ts`).

## 4. Какие данные видит автор заявки

Показ резюме нанимающему руководителю внутри своей компании — это обработка **тем же оператором**, а не передача третьим лицам. Закон её не запрещает и отдельного согласия кандидата на это не требует. Работает принцип соответствия объёма целям обработки (ст. 5 ч. 5 152-ФЗ), поэтому состав полей определён целью «решить, подходит ли кандидат».

| Поле | Автору заявки | Почему |
|---|---|---|
| ФИО | **да** | руководитель всё равно увидит человека на собеседовании; без имени ломается рабочая коммуникация |
| Фото | **да** | заказчик может узнать бывшего коллегу или знакомого — это часть решения о найме |
| Возраст | **да** | то же |
| Должность, город, ожидания по ЗП | **да** | прямо нужны для решения |
| Опыт, навыки, образование | **да** | основа решения |
| **Телефон, email, мессенджеры** | **нет** | связь с кандидатом организует рекрутер; для отбора контакты не нужны |
| Ключ резюме на площадке | нет | косвенный идентификатор, для решения не нужен |

Если политика обработки ПДн компании потребует слепого отбора, включается `HR_ANONYMOUS_SCREENING=true` — тогда скрываются ФИО и фото, остальное остаётся.

### Организационные условия (вне кода, обязательны)

1. Руководители, получающие профили кандидатов, внесены в **перечень лиц, допущенных к обработке ПДн**, приказом по организации.
2. Доступ ограничен своей заявкой — реализовано в коде.
3. Обращения фиксируются в журнале действий: `hr.candidate.view_pii`, `hr.hiring_request.submit_candidates`, `hr.hiring_request.decision`, `hr.candidate.import.farpost`.
4. Политика обработки ПДн дополнена разделом о подборе персонала и об импорте резюме с внешних площадок.

## 5. Сроки хранения — что говорит закон

**Конкретного срока хранения резюме в 152-ФЗ нет.** Действует принцип: данные хранятся не дольше, чем требует цель обработки (ст. 5 ч. 7), и уничтожаются по достижении цели.

Сроки уничтожения:

| Основание | Срок |
|---|---|
| Цель обработки достигнута (решение по вакансии принято) | **30 дней** |
| Отзыв согласия субъектом | **30 дней** |
| Требование субъекта (данные неточные, неполные, получены незаконно) | **7 рабочих дней** |
| Выявлено нарушение обработки | до **10 дней** |
| Технически невозможно уничтожить в 30 дней | до **6 месяцев**, но с блокировкой данных в течение 30 дней |

**Расхождение ведомств, которое нужно знать.** Роскомнадзор считает, что ПДн отклонённого кандидата уничтожаются в течение 30 дней после решения. Приказ Росархива № 236 от 20.12.2019 (ст. 438) устанавливает для документов лиц, не принятых на работу, срок **1 год**. Ведомства спорят, считать ли резюме «архивным документом»; однозначного ответа нет. Консервативный выбор — ориентироваться на РКН.

**Кадровый резерв** возможен только при **отдельном согласии кандидата с указанием срока хранения** (практика — 6–12 месяцев). С 01.09.2025 согласие оформляется самостоятельным документом. По истечении срока составляется акт об уничтожении.

### Что из этого следует для системы

Предложенный ранее единый срок «180 дней для всех» **неверен**. Ретенция должна быть привязана к событию и к наличию согласия:

1. Кандидат под конкретную вакансию, без согласия на резерв → обезличивание через **30 дней** после закрытия вакансии или отказа.
2. Кандидат с согласием на кадровый резерв → хранение до срока из согласия, затем обезличивание и акт.
3. Отзыв согласия → обезличивание в 30 дней; требование субъекта об удалении → 7 рабочих дней.
4. Обезличивание, а не удаление строки: сохраняются `id`, этап, источник, даты — чтобы отчётность за прошлые периоды не ломалась.

Это задачи 6–7 бэклога (`HH_HR_BACKLOG.md`), и их нужно закрыть до появления в базе реальных кандидатов.

⚠️ Формулировки согласия, политики и приказа о допущенных лицах должен проверить юрист. Настоящий документ — техническая рамка, а не юридическое заключение.

## 6. Ответственность

Нарушения обработки ПДн наказываются по ст. 13.11 КоАП (после реформы 2024–2025 суммы существенно выросли, за утечки введены оборотные штрафы), за незаконное использование ПДн предусмотрена уголовная ответственность по ст. 272.1 УК РФ (введена в 2024 году). Конкретные размеры на дату внедрения уточнить у юриста.
